# VariableBox 重构教训与技术复盘：当自动化遇上环境摩擦

> **核心感悟**：技术的价值在于解决问题的收益，减去引入该技术所带来的环境摩擦力。如果投入产出比（ROI）为负，应果断舍弃“核武器”，回归“大道至简”。

---

## 一、 背景：为何要引入 Source Generator？

在 `VariableBox` 的重构中，我们面临 11 个数值类型（`int`, `double`, `decimal` 等）的具体类定义。这些类逻辑高度相似：
- 继承自 `NumericUpDownBase<T>`。
- 指定对应的 `NumericOperations`。
- 重写 `StyleKeyOverride`。

为了追求“100% 自动化”和“零样板代码”，我们尝试引入了 Source Generator（源生成器）来动态生成这些包装类。

## 二、 惨痛教训：陷入的“技术黑洞”

在开发过程中，我们先后遇到了 5 个核心摩擦点，导致开发陷入“死循环”：

### 1. 编译器的“时差” (XAML vs C#)
Avalonia 的 XAML 编译器是基于 MSBuild 任务的。它在扫描“本地类型”时，往往无法及时解析到存在于内存中的生成代码。
- **现象**：C# 编译通过，但 XAML 疯狂报错 `AVLN2000`。
- **代价**：必须引入 `XmlnsDefinition` 这种强行“锚定”映射的方案来补救，增加了命名空间管理的复杂度。

### 2. Partial 类的“构造函数陷阱”
为了让 IDE（Rider/VS）支持代码跳转和智能提示，我们必须手动写下 `partial class` 的占位符。
- **冲突**：一旦手动写了继承关系，C# 编译器就要求在手动部分也能解析基类的带参构造函数。
- **后果**：我们在“把继承写在生成器”和“把继承写在手写代码”之间反复横跳，顾此失彼，陷入死循环。

### 3. 环境兼容性的负担
Source Generator 项目必须强制使用 `netstandard2.0`。
- **问题**：在 `netstandard2.0` 下使用现代 C# 语法（如文件范围命名空间、记录类型等）需要大量的额外配置。
- **讽刺**：为了省掉 50 行简单的代码，我们写了 200 行复杂的 Roslyn 分析代码。

### 4. 跨项目可见性难题
生成的类在库项目内部可见，但在 Demo 或测试项目中经常因为 DLL 元数据还没更新而找不到类型，导致 UI 预览和单元测试频频罢工。

## 三、 学习心得：如何判断“技术过载”？

通过这次复盘，我们总结了三条评估准则：

1.  **数量级准则**：
    - 如果样板代码只有 10-20 个，且结构固定，**手写是最高效的**。
    - 只有当数量级达到 100+ 或逻辑极其复杂（如 Dapper 的映射）时，才考虑生成器。

2.  **摩擦力准则**：
    - 关注“环境摩擦力”。如果一项技术需要你不断通过“打补丁”（如 `XmlnsDefinition`、`EmitCompilerGeneratedFiles`）来维持运行，说明该技术与当前环境（Avalonia XAML 编译器）的契合度较低。

3.  **可维护性准则**：
    - 代码生成的另一面是“黑盒”。手写的 50 行代码，任何新手都能修；生成器的 200 行代码，只有对 Roslyn 极度熟悉的人才能维护。

---

## 四、 最终架构：大道至简

我们最终选择了**“泛型核心 + 手写极简包装类”**的架构。

### 现在的优点：
- **IDE 体验完美**：智能提示、代码跳转瞬间完成，无需等待生成。
- **XAML 解析稳健**：命名空间路径清晰明确，不再有找不到类型的诡异报错。
- **维护零负担**：新增类型只需复制一行代码，成本几乎为零。
- **结构清晰**：所有的业务逻辑都在泛型基类中，具体的 11 个类只是“类型声明”。

---

## 五、 总结

不要因为有了“核武器”就拒绝使用“扳手”。在 UI 库开发中，**“可预测性”和“稳定性”永远高于“炫技式的自动化”**。
